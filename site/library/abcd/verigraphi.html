01

First, picture the problem.

Separately generated modules may disagree about port widths, names, or reset conventions even when each compiles alone.

↳Two plumbers can build perfect pipes that still do not join if they assume different connector sizes.
02

Make it concrete.

An 8-bit sender and a 16-bit receiver

Interactive · toy example

The toy contract requires equal widths. Change the receiver width and see whether the connection is structurally compatible.

Sender width 8, receiver width 16: this toy contract rejects the connection unless an explicit conversion is specified. Width 8 on both ends passes this structural check, but behavior and timing still need validation.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Extract architecture

Analyze specification documents into roles, interfaces, and an implementation plan.

02

Build the graph

Represent hierarchy, port-level wiring, and dependencies as typed relationships.

03

Generate with context

Produce pseudocode and RTL incrementally, with compilation feedback.

The contribution: A specification-anchored graph that makes structural design intent explicit before and during hierarchical generation.

04

Bring the idea to ABCD.

A possible research direction
Specification document→Shared interface graph→Consistent module generation

ABCD could retain a checkable interface contract across planning, RTL generation, and software mapping.

Small experiment: Deliberately disagree on width, reset polarity, and signal direction in three module descriptions. Record which errors are caught structurally.

Keep in mind: A valid connection graph does not prove correct cycle-by-cycle behavior. Keep structural checks distinct from functional validation.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.

05

Read the result in context.

RV32I case study
183 tests

The reported processor passes the stated submodule and randomized arithmetic tests.

Additional evaluation scope
3 NIST specs

The paper includes specification-driven designs alongside its processor example.

Scope matters. The RV32I cost summary says its hierarchy-analysis stage was skipped. That case alone cannot isolate the benefit of constructing the knowledge graph. Tests are not an exhaustive proof.
