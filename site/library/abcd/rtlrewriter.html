01

First, picture the problem.

Correct RTL may contain expensive structural choices. Rewriting it is useful only if the original behavior is preserved.

↳Rearrange a workshop to share a tool without changing what the workshop produces.
02

Make it concrete.

Select before or after addition?

Interactive · toy example

If select = 0, output a + b; otherwise output c + d. Try both circuit arrangements with a = 2, b = 3, c = 7, d = 4.

Two-adders form: compute 2 + 3 = 5 and 7 + 4 = 11, then select. Shared-adder form: select (2,3) or (7,4), then add. Both give 5 for select 0 and 11 for select 1 under the same arithmetic widths.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Partition the circuit

Use estimated synthesis cost to divide large RTL into manageable pieces.

02

Propose informed rewrites

Combine code/diagram analysis, retrieved knowledge, and cost-aware tree search.

03

Check and measure

Filter candidates through verification and synthesis feedback.

The contribution: An RTL-optimization workflow combining partitioning, multimodal analysis, retrieval, cost-aware search, and accelerated verification.

04

Bring the idea to ABCD.

A possible research direction
Existing RTL→Behavior-preserving alternatives→Measured PPA trade-offs

Treat rewriting from synthesis feedback as prior work; compare ABCD’s architectural changes with local RTL optimization.

Small experiment: Try the mux/adder rewrite with fixed widths and signedness. Check equivalence, area, and timing in the same tool flow.

Keep in mind: Arithmetic width, overflow, reset, and latency conventions matter. Fewer operators in source code do not guarantee a better synthesized circuit.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.
