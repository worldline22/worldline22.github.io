01

First, picture the problem.

Unstructured descriptions mix module boundaries, connections, behavior, and testing requirements. A generator can lose track of any of them.

↳A building blueprint tells you which rooms connect. A room specification says what equipment and activities belong inside.
02

Make it concrete.

Two views of a tiny accumulator

Interactive · toy example

An input register feeds an adder, which updates a sum register. Switch from the connection map to the sum register’s behavior contract.

Topology: input → adder → sum register, with the old sum fed back to the adder. Behavior: reset makes sum 0; a valid input adds its value; without a valid input, sum holds. Both views are needed to describe the same circuit.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Describe topology

Architectural Sketch captures modules, ports, and interconnections.

02

Describe operation

Operational Specification records each module’s function and interfaces.

03

Debug with evidence

Agents use test feedback and selected simulation probes to refine the generated design.

The contribution: Two structured hardware representations connected to a planning, generation, verification, and debugging workflow.

04

Bring the idea to ABCD.

A possible research direction
Topology + behavior→Traceable module contracts→Generated and tested RTL

This is a direct reference when specifying ABCD’s architecture and command-level representations. Compare their semantics, not just their names.

Small experiment: Give two descriptions of an accumulator that disagree about reset. Check whether the framework detects the conflict before RTL integration.

Keep in mind: A representation helps organize a design; it does not by itself establish executable mapping or enforcement of system-wide PPA budgets.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.

Case studies
