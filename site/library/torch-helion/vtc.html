01

First, picture the problem.

A tensor is an array of numbers. Splitting or rearranging it can create temporary arrays, even though the numbers themselves do not change.

↳Think of a library catalog: it tells you where a book lives. You do not need to photocopy the book onto a new shelf.
02

Make it concrete.

Split an array without copying it

Interactive · toy example

Read the last three elements of A. Switch between a physical copy and a virtual view: the answer stays [40, 50, 60].

A = [10, 20, 30, 40, 50, 60]. A copied slice stores [40, 50, 60] in 3 extra slots. A virtual slice uses the rule view[i] = A[i + 3] and stores no extra values.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Describe the mapping

Record which original tensor and index hold each value.

02

Rewrite kernel I/O

Adjust reads and writes around the calculation, including between separate kernels.

03

Keep profitable choices

Profile alternatives and resolve conflicting transformations. An awkward access pattern can erase the savings.

The contribution: A general virtual-tensor representation plus a search for profitable data-movement elimination. Efficient contiguous chunks can be enough; the whole tensor need not be contiguous.

04

Bring the idea to Torch-Helion.

A possible research direction
Tensor access rules→Address mappings→Fewer intermediate copies

Consider expressing split, reshape, and cache-update patterns as address rules in Torch-Helion, with legality conditions that preserve the original reads and writes.

Small experiment: Compare a materialized intermediate with direct destination writes. Check numerical equality, bytes moved, peak memory, and measured kernel latency.

Keep in mind: Removing a copy does not automatically improve runtime. Verify memory access efficiency and the replacement compute kernel.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.

05

Read the result in context.

Average reported speedup
1.28×

Against the best of four compiler baselines for each tested case on NVIDIA A100 and H100. Maximum: 1.93×.

Average peak-memory savings
17.5%

Against PyTorch on A100 at batch sizes 1 and 16. Maximum: 60%.

Scope matters. The main suite uses selected layers or blocks from five model families. Against specialized vLLM, the tested Llama decoder layer improves only 1.011× on A100, with no improvement on H100.
