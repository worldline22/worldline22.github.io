01

First, picture the problem.

Optimizing only the operator graph or only a kernel’s tile size can miss transformations that need both algebraic changes and a different GPU execution structure.

↳Reorganizing a kitchen can mean changing the recipe, sharing work among stations, or changing what each cook keeps within reach. Mirage searches across those levels.
02

Make it concrete.

Different expression. Same answer?

Interactive · toy example

Let A = 2, B = 3, and C = 4. Explore a valid distributive rewrite and an invalid candidate. This is a scalar analogy for candidate checking.

Original: A × (B + C) = 2 × 7 = 14. Distribute: A × B + A × C = 6 + 8 = 14. Incorrect candidate: A × B + C = 6 + 4 = 10. A single matching example would not prove equivalence.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Represent three levels

Nested µGraphs describe kernels using device memory, blocks using shared memory, and threads using registers.

02

Search and prune

Abstract expressions reject unpromising structures before more expensive equivalence checks. The supported LAX class uses addition, multiplication, and exponentiation.

03

Finish the implementation

For accepted candidates, optimize layouts, operator scheduling, and memory plans, then profile generated kernels.

The contribution: A multi-level graph representation and superoptimization pipeline that jointly explore algebraic and hardware-level program alternatives.

04

Bring the idea to Torch-Helion.

A possible research direction
Equivalent tensor expressions→Multi-level execution graph→Profiled kernel candidates

Explore a small set of algebraically valid alternatives before Helion schedule tuning. Keep correctness checks distinct from performance ranking.

Small experiment: Compare two forms of a small fused expression. Validate their outputs over varied inputs, measure error in the target precision, and profile several tile schedules.

Keep in mind: Algebraic equivalence and floating-point behavior are different questions. One matching numerical example proves neither general equivalence nor numerical stability.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.

05

Read the result in context.

Model-level relative performance
0.9–1.9×

Reported when integrating optimized kernels into four DNNs, compared with native PyTorch implementations. Some cases are slower.

Optimization time
Up to 4 h

Reported search time for a tensor program in the evaluation. This is an upfront compilation cost.

Scope matters. The formal randomized-verification guarantees have a stated algebraic scope. §7 says the implementation uses one randomized test with fixed small primes; the stronger final theoretical check was planned. Do not read the result as unconditional correctness for arbitrary GPU code.
