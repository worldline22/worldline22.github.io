01

First, picture the problem.

A schedule decides more than layer order. It must divide accelerator resources, handle dependencies, and choose how groups of inputs move through the layers.

↳A workshop can give every worker to job A and then job B, or split the workers into two teams. A larger job can combine both arrangements.
02

Make it concrete.

Two independent tasks, four cores

Interactive · toy example

Switch between a T cut and an S cut. The picture shows resource ownership, not measured duration. A and B have no dependency in this toy.

T cut: A uses cores 0–3, then B uses cores 0–3. S cut: A owns cores 0–1 and B owns cores 2–3; they may run together. With a dependency, B must still wait for the data it needs.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Define the space

A resource-allocation tree records nested spatial cuts, temporal cuts, and subbatch sizes.

02

Evaluate each plan

Estimate compute, communication, buffering, and pipeline gaps under the target hardware configuration.

03

Search tree changes

Simulated annealing explores inter-layer plans, paired with an intra-layer mapping engine.

The contribution: A unified notation for a broader inter-layer scheduling space and a search framework for exploring it. The search is heuristic, not a proof of the best possible tree.

04

Bring the idea to Torch-Helion.

A possible research direction
Layer dependency graph→Nested space/time choices→Resource-aware schedule

A Torch-Helion planner could represent both sequential sharing and spatial partitioning, rather than limiting a fusion group to one execution pattern.

Small experiment: For a small branched graph, enumerate a few nested S/T trees. Compare modeled traffic, memory capacity, and idle time; validate the best candidates on the intended backend.

Keep in mind: An S cut can create load imbalance and pipeline fill/drain gaps. A T cut gives each child more cores but limits overlap.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.

05

Read the result in context.

Performance vs. Tangram
