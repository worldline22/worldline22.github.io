01

First, picture the problem.

Every operator has many tile, storage, and execution-order choices. Fusion links neighboring choices together, so the number of complete plans grows rapidly.

↳Think of jigsaw pieces with the same connecting edges. If one costs more in every relevant way, you can discard it before assembling the whole puzzle.
02

Make it concrete.

Which plans are safe to discard?

Interactive · toy example

These three toy plans have the same boundary interface, equal energy, and the same memory-lifetime pattern. Lower time and lower memory are better.

Plan A: time 2, memory 8. Plan B: time 3, memory 3. Plan C: time 4, memory 9. C is dominated by A and B. A wins with budget 8; B wins with budget 3; neither fits budget 2.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Keep boundary information

Track shared tile shapes, storage locations, and exchange order to recognize compatible partial mappings.

02

Keep the Pareto frontier

Remove a plan only when another compatible plan is no worse in all relevant costs and resource requirements.

03

Join + prune again

Compose survivors and retain memory-reservation information, so pruning preserves the supported optimum.

The contribution: Identifying the sufficient interface and resource information that makes early pruning safe. Memory lifetimes matter, not just a single peak-memory number.

04

Bring the idea to Torch-Helion.

A possible research direction
Compatible partial schedules→Safe dominance pruning→Smaller fusion search

Torch-Helion could retain several useful plans per boundary interface instead of only the locally fastest one. Pruning must account for resources and their lifetimes.

Small experiment: On a tiny supported graph, compare pruned search with exhaustive enumeration. Require the same best modeled result before trying larger graphs.

Keep in mind: The table below simplifies the paper’s pruning conditions. Real plans also need energy, compatibility, and reservation information to justify safe removal.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.

05

Read the result in context.

CPU-hours to find the optimum
≈1.5

One transformer mapping experiment. Reconstructed baseline searches remain short of optimality at 10,000× this search-time budget; baseline times use cached evaluations.

Reduction in energy × delay
Up to 1.8×

A separate modeled accelerator comparison against TransFusion. This is a performance/energy objective, not a search-time ratio.

Scope matters. The 10,000× comparison is about finding a mapping, not running a neural network. Optimality is limited to the supported search space and hardware model.
