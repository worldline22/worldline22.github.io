01

First, picture the problem.

Small independent kernels can repeatedly exchange results through slower memory. A fixed piece size also leaves room unused when later stages produce smaller tensors.

↳A small kitchen counter fits one large tray or two small trays. A good cook changes the work schedule as the trays get smaller.
02

Make it concrete.

How many image tiles fit on the counter?

Interactive · toy example

The toy fast memory has 8 slots. One early-stage image tile takes 6; one later-stage tile takes 3. Change the stage and number of tiles.

Early stage: 1 × 6 = 6 of 8 slots, so one tile fits. Later stage: 2 × 3 = 6 of 8 slots, so two tiles fit. Three later-stage tiles require 9 slots and exceed capacity.

Invented teaching example. Values and costs here are not measurements from the paper.

03

What did the paper add?

01

Group the graph

Use hardware information to construct coarse subgraphs spanning layers or blocks.

02

Choose tiles + order

Split subgraphs into pieces and exploit uneven memory needs across network stages.

03

Generate joint kernels

Reuse local buffers and schedule across layers to overlap eligible transfers and calculations.

The contribution: Hardware-aware graph partitioning connected to memory-sensitive scheduling and cross-layer kernel generation. Different stages can use different execution granularities.

04

Bring the idea to Torch-Helion.

A possible research direction
Architecture memory limits→Fusion + tile decisions→Cross-layer schedule

Make memory capacity and hierarchy explicit inputs to Torch-Helion’s planner. Let fusion groups and tile sizes change when the architecture profile changes.

Small experiment: Run the same two-stage graph under two local-memory budgets. Check that selected groups and tiles change, then measure traffic and latency.

Keep in mind: The illustration counts only working tiles. A real capacity check must also include weights, outputs, alignment, and double buffering.

This connection is an interpretation for the project, not an implementation or performance claim by the paper.

05

Read the result in context.

Average throughput vs. TVM
11.15×

Reported on the STCP920 specialized accelerator. The gain over a reproduced AStitch implementation is 6.16×.

Narrower GPU case study
1.06×

Reported on A100 against CUTLASS with convolution fusion. This comparison has a different scope from the main accelerator suite.

Scope matters. The large headline gains are specific to the specialized accelerator evaluation. The implementation does not support dynamically shaped tensors.
